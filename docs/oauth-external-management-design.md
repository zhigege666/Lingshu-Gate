# Administrator OAuth for external configuration

[简体中文](zh-CN/oauth-external-management-design.md) · [External configuration](external-mcp-configuration.md) · [Built-in OAuth](builtin-oauth.md)

This **unreleased development implementation** adds a separate, default-disabled built-in OAuth management resource. It does not enable a production endpoint, provision a client or key, or certify real-client integration. The released 0.4.3 version and its artifacts are unchanged.

## Explicit setup and resource isolation

Save and enable the existing built-in OAuth server with trusted HTTPS URLs and an active signing key. In **Connection infrastructure**, explicitly enable **Separate management connection**. The management URL is derived from the saved business resource origin as `https://gate.example.test/mcp/manage`; its protected-resource metadata is `/.well-known/oauth-protected-resource/mcp/manage`. It is not an OAuth callback. Enabling requires a current administrator with `operations.manage`; private Console writes additionally use strict Origin, live-session CSRF, revision CAS and atomic redacted audit. No key or client is generated by enabling.

Register or explicitly edit a static client's allowed resources: **Business /mcp**, **Management /mcp/manage**, or **Both resources**. Existing clients migrate to business only. Management requires the client's explicit `operations.manage` scope; apply, cancel and remote probe also require `tools.invoke`. Business `tools.read`/`tools.invoke` and management rights are separately evaluated. A registered client allowed for both still needs distinct authorizations and refresh families for each exact resource.

The administrator creates a fresh management connection requesting the exact resource and its scopes through the existing authorization-code/S256 flow. The public consent page names the client, resource, requested scopes, current administrator, eligible configuration tools and individually entered initial targets/actions. Nothing is inferred from an ordinary business connection. Operator roles, an external issuer, a business bearer, API tokens and Console cookies cannot authenticate `/mcp/manage`.

The invoked route chooses the verifier's exact expected resource from trusted configuration before authentication. JWT claims, request arguments, Host and forwarded headers cannot choose another audience. Wrong-audience access tokens, codes and refresh tokens are rejected in both directions, even for the same issuer/key/user/client. Management verification failure never falls back to another issuer, an API token or a cookie. Disabled management returns no management catalog. Enabled unauthenticated management returns a 401 challenge with path-specific metadata and explicit management scopes.

Ordinary `/mcp` keeps its business metadata, challenge and scopes; it rejects `operations.manage`. The shared authorization-server metadata continues advertising business scopes. Management protected-resource metadata and challenges explicitly advertise `operations.manage` and `tools.invoke`. RFC 8414 permits supported scopes to be omitted from that advertisement; MCP describes challenge-first scope selection. This implementation does **not** prove that a real client requests those management scopes. See [RFC 8414 section 2](https://www.rfc-editor.org/rfc/rfc8414.html#section-2) and [MCP scope selection](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#scope-selection-strategy). Official client authentication/developer-mode guidance was reviewed on 2026-10-04; actual connection/request/cache behavior remains unverified.

## Fixed tools and exact targets

| Tool | Management scope ceiling |
|---|---|
| `gate_mcp_config_plan` | `operations.manage`; a remote probe additionally needs `tools.invoke` |
| `gate_mcp_config_status` | `operations.manage` |
| `gate_mcp_config_apply` | `operations.manage` + `tools.invoke` |
| `gate_mcp_config_cancel` | `operations.manage` + `tools.invoke` |

Management discovery and dispatch permit only the consented subset of these four built-ins with current schema fingerprints. No business/downstream tool or unrelated built-in is visible or callable through this resource. A read-only `operations.manage` family cannot acquire write access by refreshing, changing targets or using a broader grant/client.

Targets are a separate map of exact server IDs to `create` and/or `update`. Initial consent requires at least one target; at most 1,000 unique targets are supported. IDs use 1–128 characters matching `[A-Za-z0-9][A-Za-z0-9_.-]{0,127}`. No wildcard, prefix, empty action list or other action is accepted. Plan checks the actual target and mode before reading target configuration or contacting a peer. Status/cancel resolve and check the operation's real target. Target authorization grants no credentials, HTTP trust, publication, ZIP/Git delivery or remote execution.

## Confirm target changes in Gate

Under **My connections → Gate built-in OAuth**, an active management grant exposes **Adjust targets** instead of the business tool-scope editor. Read-only details retain exact targets and consented tools for historical review. The owner edits a complete target policy across 10-row pages; pagination cannot drop other targets. Removing every target is allowed here and denies every target operation.

The private Console flow is:

1. `GET /v1/auth/oauth/grants/{grant_id}/management-targets` obtains current targets/revisions and a session-bound options ticket.
2. `POST .../management-targets/preview` validates the exact policy and both expected revisions, and returns previous/next targets with a bounded confirmation.
3. After explicit review, `POST .../management-targets` consumes the latest confirmation, rechecks live authority and bound dependencies, updates that grant by CAS, increments its target/grant revisions and records redacted audit in one writer transaction.

These endpoints require the actual grant owner, a current administrator, `operations.manage`, `tools.invoke`, a live private Console session and strict Origin/session checks. API/OAuth bearers cannot edit targets through `/v1`. Tickets bind user/session, grant/client/resource/configuration revisions, current target/tool digests and the exact proposal. Confirmations expire within ten minutes, are single-use and have existing global/user capacity limits. Expired, replaced, foreign-session and stale confirmations fail closed; audit failure rolls back the change and consumption.

The same management JWT follows the explicitly changed live target policy on its next verified request. Existing plans become stale. JWT scopes, family scopes, consented tools, business grants and other users' grants do not expand. Dirty or pending dialogs protect input and keyboard close; errors remain visible with reload/review recovery, while saved feedback is brief.

## Execution and recovery

Every dispatch and worker boundary reloads current issuer/resource, client, grant, refresh family, administrator role/permissions, expiry, target revision and tool fingerprint. Required scope is the JWT/client/grant/family/current-permission/delegation intersection. Checks occur after waits and before file persistence, runtime application, connection and discovery; revocation or role downgrade blocks later side effects.

Plans and idempotency bind the verified management connection's issuer/resource/client/grant/family, current target revision and tool snapshots, in addition to existing actor, manifest/file/credential/action digests. Authority is rechecked before returning a cached completion. Another connection or changed policy cannot reuse that plan/result to bypass authorization. No raw inbound bearer is persisted in a plan or journal.

The shared [external workflow](external-mcp-configuration.md) retains offline planning, explicit probe/apply/cancel, five-minute single-use plans, CAS, atomic journal completion, cooperative deadlines, connection ownership, secret redaction and reconciliation of interrupted results. Existing managed credential references and approved private-HTTP trust can be used but are not created. Discovery quarantines changed classifications; it does not publish them or grant business access. `instance_id=server_id` remains one configuration per target. Groups, fixed catalogs, multi-instance routing and the production safe Git executor are outside this change.

Disabling management revokes only management families and pending management codes; business families retain their rights. Disabling or changing the underlying built-in issuer/resource also turns management off, and does not silently re-enable it later.

## Validation and remaining acceptance

The bounded synthetic ASGI test file `tests/test_oauth_management_e2e.py` runs real inbound authorize → consent → code/token → management MCP → confirmed external configuration, with temporary signing keys and a fake downstream HTTP peer. It covers bidirectional resource substitutions, ordinary/external/non-admin/read-only denial, exact targets, target CSRF/CAS/audit rollback, same-JWT target updates, old-plan/idempotency isolation, queued revocation/expiry/role changes, cancellation and redaction. Its latest run completed with 19 passed in 25.67 seconds under a 180-second command deadline. The complete backend run completed with 1,369 passed and three existing peer-fixture skips; no management test was skipped.

Built-asset browser tests separately cover bilingual light/dark layouts at 1600×900, 1920×1080, 2560×1080 and 2560×1440, explicit resource/scope choices, body-bound CSRF, complete 1,000-target editing, fixed actions, keyboard guards and local validation recovery. The final affected-page browser run completed with 141 passed in 6.4 minutes, including all 40 new management cases; frontend unit tests completed with 70 files / 426 tests passed. Type/source-contract checks and both asset builds passed. They use mocked UI responses and cannot replace ASGI security tests, independent pixel review, production TLS or a real client's management-scope request and cache behavior. No publication, live credentials or real peer acceptance is claimed.
