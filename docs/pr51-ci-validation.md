## False-positive data-flow evidence

1. **Benchmark logging.** SARIF traces `scripts/benchmark_tool_catalog.py:132` → `scope_cases.oauth_catalog_ceiling` → the final JSON print. The source is `{"code": error.code, "elapsed_ms": ...}`, immediately after asserting `error.code == "tool_catalog_limit"`. The classifier's password-name heuristic includes `oauth`; it labels this statistics variable as a password. A completed synthetic run with 5,000 services, 50,000 tools and one iteration produced only `code=tool_catalog_limit` and a numeric elapsed time at this field. It issued no credentials and contacted no downstream.
2. **Token hashing.** SARIF traces `create_api_token` results and the fixture's `oauth_sessions` values to `hash_secret`. The broad password heuristic includes `api_token` and `oauth`. `AuthStore.login` and `AuthStore.create_api_token` generate the hashed values with `secrets.token_urlsafe(32)` (256 random bits); OAuth client secrets use 48 random bytes. The values are lookup/binding tokens. Human passwords take `hash_password`/`verify_password`, using a random salt and 200,000 PBKDF2-HMAC-SHA256 rounds. Changing this lookup hash would alter persisted token identities without improving password security.
3. **Git fixture hashing.** SARIF starts at the fixed synthetic test value in `test_reflected_bare_basic_or_proxy_secret_never_reaches_snapshot`, encodes it into a raw blob, and reaches `ObjectFixture.add`. That function computes SHA-1 over the exact Git `<kind> <length>\0<data>` representation. The acquisition then rejects the reflected content with `git_snapshot_content_rejected` and closes the object streams. This is neither password storage nor authentication; replacing SHA-1 would invalidate the fixture's declared SHA-1 Git format and its object-verification coverage.

## Follow-up regression evidence

The benchmark now calls its internal result `catalog_limit_stats`; the published `scope_cases.oauth_catalog_ceiling` key is unchanged. The output is constructed from the literal `tool_catalog_limit` and numeric elapsed milliseconds, without copying exception values or messages. [`test_catalog_benchmark_reporting.py`](../tests/test_catalog_benchmark_reporting.py) enforces the two-field allowlist, fixed outcome and numeric timing. The same full Python CodeQL suite scanned all 305 follow-up files and found six results: token hashing and Git fixture hashing, plus the four unchanged findings outside the original PR check. The benchmark finding is absent, and no new rule/file pair appeared. The pushed SHA's GitHub scan must still be read independently.

[`test_builtin_oauth.py`](../tests/test_builtin_oauth.py) now checks the existing SHA-256 encoding against a fixed public-metadata vector. Tests observe the real random generator rather than substituting token values: Console and consent sessions/API tokens request 32 bytes, OAuth client secrets 48 bytes. They verify persisted lookup identities, reopening the store, forged-token rejection and logout/revocation. A separate test observes the real PBKDF2 call through user creation, password replacement and successful/failed login: all five operations use SHA-256, a 32-character salt and 200,000 rounds; replacement changes the salt, and human passwords never enter `hash_secret`. The existing unknown-user test checks the same PBKDF2 work and uniform rejection. The reflected-content Git tests now also assert that every opened object stream is closed. Hash algorithms, persisted identities and Git object format are unchanged; no `usedforsecurity` override was introduced.
