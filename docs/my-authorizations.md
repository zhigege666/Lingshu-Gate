# My authorizations

[简体中文](zh-CN/my-authorizations.md) · [Built-in OAuth](builtin-oauth.md)

This guide describes the current development source. It does not assert publication, deployment or real-client acceptance.

## One personal entry

**My authorizations** combines personal Gate API tokens, Gate OAuth grants and external-provider grants. Authentication type remains a property of each record; the underlying credentials, protocol and revocation targets remain distinct. The legacy personal-token bookmark opens the combined page with the API-token filter. Revoking one record affects that source record only. Each source reports loading failures separately; a partially loaded list is not a complete total.

Use the primary **Create API token** button to open its form directly. **Other connections** contains the OAuth guide and external-provider grant entry. OAuth grants still originate from the client's actual authorization flow. An API-token secret appears only in the successful creation response and one-time display; listing records never recovers it. Scope and quota edits require the active owner's Console session and `credentials.manage.self`.

## Functional permissions

The API-token editor uses **MCP scope**, **Functional permissions**, and **Call limits** tabs for one shared draft. The MCP list shows four scope choices directly in each row. Choosing **Selected tools**, or its selected-tool count, opens the exact tool picker. Collapsing, searching, paging, or switching tabs does not submit or discard edits. Refresh preserves the draft and unavailable selections. An explicit MCP scope choice also adds its required read/write functional permissions, limited to the current owner’s grantable permissions. Expanding an existing token shows those additions before the write; manually removing a required permission makes the conflict visible. New and existing tokens offer account-following and independent scope. Switching retains the inactive independent draft locally and submits only the active mode. Saving still uses the backend preview and confirmation ticket; an extra review screen appears only when existing access expands.

Select the **Functional permissions** tab in the API-token editor to review the full available scope. Permission groups follow one continuous vertical reading order; permissions within each group use two columns when the editor has enough room and one column when it does not. Short groups do not reserve the height of neighboring groups. Names, scope identifiers, descriptions and switches remain visible, while the dialog actions stay outside the scrolling content. The layout preserves current selections, including saved permissions that are no longer in the current catalog; it does not add scopes merely by opening or rearranging the permission groups.

## MCP scope

API tokens and Gate business OAuth offer four direct choices: **No access** (OAuth: **None**), **Service read**, **Service read/write**, and **Selected tools**. Service read/read-write is continuous authorization; service read/write can include future synchronized write tools. Selecting all current tools retains a snapshot and does not imply continuous authorization. A service cannot simultaneously use continuous and selected-tool modes in the same authorization.

Continuous authorization is implemented for independent Gate API-token scopes and Gate business OAuth grants. Later tools join a previously chosen continuous service scope after synchronization, within current account resource permissions, functional scopes and the effective `required_access` policy. No review or publication step is required. External tools default to write; only a trusted local override or Gate-owned contract can classify them as read-only. Read-only continuous policies never acquire write tools. Changes to service identity or local access policy can invalidate an exact snapshot and require an explicit update; ordinary tool synchronization does not add IDs to a selected-tool scope.

Service policies bind the MCP lifecycle identity. Deleting/recreating a service or replacing its trust target does not transfer old authorization merely because its ID or name is reused. A display rename or ordinary upgrade that preserves the trusted identity preserves continuous intent. API-token selected snapshots also bind service identity. Tool access policy, discovery, authorization and deployment retain separate responsibilities.

Existing selected-tool OAuth grants retain their saved snapshots. Legacy API tokens without a policy continue to follow account access with no invented quota. The owner can explicitly create an account-following token or switch either way between account-following and independent scope. Account-following tracks current and future account resource permissions within the token’s functional scopes and call limits; an empty independent scope grants no business MCP access. Switching mode retains owner checks, revision/catalog binding, confirmation tickets and audit, and does not reset the token’s consumed rate budget.

External-provider grants retain their existing provider/local allowlist contract and do not offer continuous MCP authorization. The separately enabled `/mcp/manage` resource retains its fixed management-tool and exact-target contract; it does not subscribe to business MCPs.

Choose **Create token** for a new token or **Save authorization** for an edit. Creation, narrowing and quota-only changes complete from that one action. An existing token that gains permissions, tools, continuous service access or a new service binding opens a change review and **Confirm expanded access**. That review groups actual changes by MCP and includes changed functional permissions or quotas; returning to editing preserves the draft. Every path still obtains a backend preview and single-use confirmation ticket for the same submitted draft. Switching service read/read-write preserves the original service binding; reconfirming a changed service remains explicit.

## Tool discovery

The Tool discovery column opens a centered editor for that record with On demand and Full tool list radio choices. **New and existing business authorizations default to on-demand**. Each API token, built-in business OAuth grant and external OAuth local grant saves its own mode; management retains fixed tools. On-demand exposes six default discovery/invocation/instance-session entries, optional authorized pins and the result reader when enabled; direct mode lists currently permitted tools. Both keep the same authority checks.

Client settings now save only the name and endpoint; generated configuration omits `tool_mode`, including when reading old browser preferences. Legacy URL/header mode hints are ignored; only the authorization setting applies. Refresh the client tool cache or reconnect after switching. Choose **Save** once; the editor performs the owner-bound preview/ticket and write sequence without a second confirmation screen. CSRF, revision checks and atomic audit still protect changes; unknown outcomes require readback before retrying. This does not edit global rules, MCP client plugin configuration or the host's local-MCP/plugin routing preference.

## Editable quotas and safe saving

New business authorizations default to **6000 calls per minute** and **100 concurrent calls**. The editable boundaries are integers **1–10000** and **1–100** respectively. Existing configured records load their actual values; opening an editor does not write defaults. For an old API token without quotas, the editor distinguishes its current **not set** values from the proposed values after saving. The existing API requires concrete quotas for an authorization update, including a permission-only change; the editor shows the current and proposed quota values. API-token and business OAuth editors save quota-only changes directly and support increasing or decreasing quotas within their supported limits. Legacy shrink-only OAuth operations keep their original contract, and quota editing does not extend expiry or increase OAuth scopes.

The backend preview identifies the exact target, policy changes, added/removed tools, future write authority and previous/new quotas, and grants nothing by itself. The explicit Create or Save action performs preview and write together for ordinary changes. An additional user confirmation is reserved for expansion of existing authority. All writes retain current permission checks, version/catalog/target binding, a single-use confirmation ticket, revision compare-and-swap and an atomic redacted audit. Audit failure rolls back the change. A quota-only save preserves stale selected snapshots and invalid service bindings; it does not reapprove them. Unknown save results retain the draft and require reading the actual state before another write; creation must not be blindly replayed to recover a lost secret.

Runtime access intersects current account/resource permissions, the token or grant policy, the effective `required_access` policy and functional scope. Gate OAuth additionally intersects the registered client, grant, JWT and family scopes. Quota changes do not reset consumed rate counts. Lowering concurrency does not cancel dispatched calls; subsequent admission uses the new limit. Business calls share a budget per API-token ID or OAuth grant ID across MCPs; listing tools is not tool execution. Counters remain limited to one Core process and reset on process restart. SQLite requires one writer/Core; the defaults do not promise measured throughput.

## Directory and verification limits

The API-token creation/editor directory currently supports a complete candidate response up to **5000 tools / 100 MCPs**. New creation beyond that bound fails explicitly; it does not silently truncate. When a larger owner's unrelated directory exceeds this limit, a smaller existing token can load its bounded saved scope with `catalog_complete=false` and `scope_editable=false` and edit quotas only. Broader API-token candidate pagination is not implemented. The separate paged OAuth editor loads service summaries in pages of 10, searches on the server, and loads tools only for the MCP being edited; search and paging preserve the authorization draft. Saved/effective scopes remain bounded and fail closed on overflow.

The Console follows the [UI interaction contract](ui-interaction-contract.md): compact tables, left labels/right controls, accessible mode radios, no repeated page introductions, and contextual errors or requested help. A source read failure is not displayed as an empty complete list.

Gate reevaluates subsequent requests and rechecks queued calls before dispatch. It does not push a replacement tool list or broaden client OAuth authorization. Clients may cache their directory and need a refresh. Actual provider/ChatGPT connection behavior, cache refresh, deployment and production capacity require separate acceptance; source and synthetic tests do not establish those outcomes.

## Saved discovery preferences

The discovery editor also manages up to 20 pins and an optional plain-text result budget. Mode, pins and budget share one revision-bound, atomic save initiated by a single **Save** action; the backend preview/confirmation protocol remains in place. Switching mode preserves other draft fields; unavailable discovery is an error, not an empty selection. Read the saved state after a conflict before saving again. Preferences preserve the credential's scope and expiry. See [pinned tools and result budgets](on-demand-tools.md#pinned-tools-and-result-budgets) for limits and group-session requirements.
