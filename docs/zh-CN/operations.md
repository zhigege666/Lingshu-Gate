# 运维

[English](../operations.md) · [文档索引](README.md)

运维 Lingshu Gate 应以证据为基础：健康探针判断服务状态，Server Status 判断下游状态，结构化事件记录状态转换，日志用于诊断，调用审计用于访问决策。

## 探针语义

| Endpoint | 回答的问题 | 应触发的动作 |
|---|---|---|
| `/healthz` | 进程和 HTTP Stack 能否响应？ | 达到受限失败阈值后重启进程 |
| `/startupz` | 应用初始化是否完成？ | 失败时继续禁止流量 |
| `/readyz` | 核心存储和请求路径能否服务？ | 失败时从路由移除实例 |

探针请求应使用短超时，并且不应要求下游服务必须健康。每个下游服务需要单独监控。

示例：

```bash
curl --fail --silent --show-error http://127.0.0.1:8000/healthz
curl --fail --silent --show-error http://127.0.0.1:8000/startupz
curl --fail --silent --show-error http://127.0.0.1:8000/readyz
```

## 下游状态

使用 `/v1/mcp/servers` 查看列表，使用 `/v1/mcp/servers/{server_id}/detail` 查看单个目标。需要区分：

- 配置和启用状态；
- 期望生命周期状态；
- 观测到的进程或连接状态；
- 健康和最近错误；
- 配置摘要；
- 工具发现数量和最近刷新结果；
- 原生受管进程的重启历史。

`desired_state=running` 是指令，不是已经执行的证明。进程 Running 之后仍要发现成功，才能作为验收证据。

控制台服务工作区在服务目录旁展示选中服务，概览、工具、日志和配置独立加载。工具可见数量对应当前登录控制台的身份，不能据此确认另一 MCP 客户端的 Token 范围或已经加载的工具目录。

按需读取详情可使用 `/v1/mcp/servers/{server_id}/detail?section=overview`。支持 `overview`、`tools`、`logs`、`events`、`configuration`、`recovery` 和 `cache` 分区。日志、事件和恢复记录的 `limit` 范围为 1–200，默认 80，控制台请求 40。概览只读取运行态；只有打开缓存分区或完整诊断时才统计缓存目录大小。不传 `section` 时保留原有完整响应。所有分区继续要求 `operations.manage` 权限；未返回的分区字段表示未请求，不能解释为零或健康。

## 工具目录

工具页采用卡片布局，支持搜索、可搜索的 MCP 服务选择、实际读写权限筛选和分页。服务选项同时显示名称和部署 ID，可区分同名的不同部署实例。具备运维权限的账号可选择尚无可见工具的已注册服务；没有运行时管理权限的账号仅看到其可见工具所属的服务。内置工具单独筛选。

每张卡片可打开完整详情，或将对应的已注册工具带入调用编辑器。打开编辑器不会执行工具，并会重置上一工具的参数与结果。发现和调用继续使用现有授权校验。

`/v1/tools` 和 `/v1/tools/{tool_id}` 在 `metadata.gate_access` 中返回当前请求的 `required_access` 与 `classification_status` 快照。读写标签使用该后端判定，不从 MCP 注解或 Manifest 默认声明推断。快照不会修改注册定义、发布分类或授予权限；实际调用时仍重新评估访问策略。

## 日志和事件

认证 Operator 可以查询：

- `/v1/logs` 和 `/v1/logs/stream`；
- `/v1/events` 和 `/v1/events/stream`。

日志描述诊断记录，事件描述状态转换和安全相关操作。应使用文档提供的 Query 参数和受限条数在服务端过滤，不要下载完整存储。

保持 `LINGSHU_GATE_LOG_PAYLOADS=false`。正常记录应包含 ID、状态、时间、计数、摘要和脱敏元数据，不应包含凭据、Authorization Header、上传 Chunk、完整工具参数或完整进程输出。

分享记录前，应检查嵌套字段，并移除接收者不需要的主机路径、用户数据和下游内容。

## 在控制台调用工具

调用工作区先选择 MCP 服务实例，再选择当前身份可见目录中的工具。内置工具单独分组。服务名称旁保留稳定的实例 ID；调用仍使用原有注册工具 ID，通过 `/v1/invoke` 完成授权和审计，不增加轮询或额外的管理权限查询。

参数默认以 Schema 驱动的表单展示，也可以切换为 JSON。两种视图编辑同一份请求数据。字段名称、说明、必填标记、默认值和示例来自所选工具的输入 Schema，说明文本不会加入请求。JSON 有语法错误时会阻止切回表单并保留输入。复杂结构保留 JSON 编辑入口；编辑普通字段不会丢弃未声明字段或改变原有数据类型。

首次选择工具会预填声明的默认值和示例，不会自动执行。**恢复默认**仅使用默认值和固定值；**填入示例**还会使用工具声明的示例。敏感字段不自动预填，没有值的必填字段需要手动补齐。调用前进行本地 JSON Schema 校验，支持 draft-07、2019-09 和 2020-12，未声明版本时按 2020-12 处理。不获取远程 Schema 引用；无法处理或无效的 Schema 会阻止调用并提示错误。后端权限、确认边界和下游校验仍是最终依据。

草稿和结果按服务身份与注册工具 ID 独立保留，仅存在于调用页内存中，不写入浏览器持久存储。离开调用页或刷新后清除。切换服务后返回的异步结果仍写回原工具。工具 Schema 变化时不覆盖草稿，会提示核对，并在运行时按最新定义校验。

## 调用审计

`/v1/access/invocation-audits` 记录工具访问决策，可用于回答：

- 谁以何种认证方式尝试调用；
- 目标服务和工具是什么；
- 操作被分类为只读还是写入；
- 哪项权限、授权或 Token Scope 决定允许或拒绝；
- 决策何时发生，以及如何关联日志和事件。

审计不是 Payload 归档。不要为了补充业务审计字段而开启 Payload 日志；应增加受限且脱敏的字段。

`GET /v1/access/invocation-statistics?hours=24` 为仪表盘提供只读聚合接口，需具备 `audit.read` 权限。`hours` 可选 `24` 或 `168`；返回总数、每 2 小时或每 24 小时的趋势，以及调用最多的 5 个工具。`requests` 统计已识别工具的调用请求，包括拒绝和未执行的尝试；`calls` 统计结果为成功或错误的已允许执行；`mcp_calls` 是其中下游 MCP 工具 ID 的子集。一次 Gate 调用只计一次，下游重试不另计。成功率以 Gate 审计结果为准，不代表下游业务结果。普通 HTTP 请求、审计前被拒绝的未知工具名，以及绕过 Gate 直接调用下游服务的操作不在统计范围内。

## 诊断

| Endpoint 或工具 | 用途 |
|---|---|
| `GET /v1/diagnostics` | 读取当前诊断快照 |
| `POST /v1/diagnostics/run` | 运行一次新的受限诊断 |
| `GET /v1/diagnostics/memory` | 查看进程内存摘要 |
| `GET /v1/runtime/environment` | 查看平台和可用运行时能力 |
| `gate_system_debug` | 通过 MCP 查询受限只读的概览、服务详情、日志、事件或诊断 |

诊断不会执行任意 Shell 命令。返回的主机元数据属于运维敏感信息，只分享调查所需的最小内容。

## 运行时缓存

`GET /v1/runtime/cache` 列出已知缓存项及其受限元数据。`DELETE /v1/runtime/cache/{cache_name}` 清除一个准确缓存项。

删除缓存是 Operator 写操作：

1. 列出条目并确认准确名称；
2. 确认该缓存可以重新生成；
3. 只清除该条目；
4. 观察下一次请求和相关事件；
5. 不要把清除持久数据或 Config 目录当作缓存处理方式。

Cache Miss 可能增加延迟或重复工具链检查，但不能绕过校验或授权。

## 日常检查

### 每天

- 校验 Readiness 和磁盘空间；
- 检查新的 Error 日志和被拒绝的调用审计；
- 检查观测状态与期望状态不一致的下游目标；
- 复核待处理的工具分类变化；
- 确认备份成功，且没有只复制在线 SQLite 状态。

### 变更窗口之前

- 记录 Gate 版本、镜像 Digest 或 `BUILD-INFO.json`；
- 记录当前 Config 和 Data 备份 Hash；
- 检查进行中的上传、构建、部署和状态未知的幂等操作；
- 定义成功、回滚和停止条件；
- 选择一个用于变更后验证的只读工具调用。

### 变更之后

- 校验三个探针；
- 使用非管理员账户登录并确认最小权限；
- 检查数据库和配置加载以及下游状态；
- 执行选定的只读调用；
- 确认审计与事件已经写入且不含 Secret。

## 故障分诊

1. 保留当前版本、配置摘要、相关 ID、时间和脱敏日志。
2. 判断影响范围是整个 Gate、单个下游服务、单个主体还是一项交付操作。
3. 访问异常时撤销具体 Token 或授权，避免关闭全部认证。
4. 只有确认准确目标和影响后才停止具体下游进程。
5. 对状态未知的交付操作，重试前先查询已有 ID。
6. 凭据可能暴露时，轮换下游凭据和受影响的 Gate Token；调查中不要打印旧值。
7. 只从与目标 Gate 版本匹配的已验证备份恢复。

不要把删除数据库、Volume、Upload 或操作记录作为第一步故障处理。保留证据是恢复和审计的必要条件。

## 容量说明

- SQLite 适合单个 Gate 进程和中等规模的单机运行。
- 长时间事件流会占用连接，应明确设置代理空闲行为。
- Upload、Build Artifact、日志和审计都在 Data 目录增长，应监控空间并按环境制定保留策略。
- 下游故障应与 Gate Readiness 隔离，但重复重试仍可能消耗资源；应使用受限的重启和请求策略。
