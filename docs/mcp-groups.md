# MCP groups

[简体中文](zh-CN/mcp-groups.md) · [Configuration](configuration.md)

This unreleased slice adds administrator-owned collections of existing MCP instances. An instance ID remains its existing `server_id`; configuration, tools, credentials, endpoints, authorization and runtime state stay with that instance. One instance may belong to several groups. Creating a group or adding a member grants no access. Existing ungrouped instances retain their behavior.

In **MCP services**, switch directly between Instances and Groups. Create or edit a group in the centered dialog, enter its name/description, choose Active or Archived, and explicitly select existing instances. Member search covers the complete metadata catalog; pagination and search retain selections from other pages. A group can contain up to 1,000 members; the store supports up to 1,000 groups. Group queries return instance metadata, not complete tool schemas. IDs remain stable when names change.

The member limit does not truncate the global instance catalog. Instance IDs/names use an immutable in-process metadata snapshot, invalidated on configuration create/update/delete/reload and bounded to 30 seconds. Explicit Refresh rebuilds it; search/page requests reuse it and filter the complete catalog on the server before paging (maximum 100 returned instances). Only IDs/names are cached, never manifests, secrets or authorization. Runtime status and current administrator authority are checked separately. Group saves reread current files under the configuration mutation lock, then check authority/CAS in the writer transaction. The backend regression uses 5,000 real synthetic manifest files and records cold/warm query timing and manifest-read counts; this is distinct from the 1,000-member mocked browser fixture and is not a production latency guarantee.

Archiving or deleting a group changes only group metadata and relationships. It does not stop, delete, reconnect or copy services, remove history, or change grants. Archived membership is retained; the Ungrouped view means no active group membership. Instance IDs and names remain visible even when an instance is missing or not loaded.

Known instance deletion invalidates its memberships before runtime/file removal; even a compensated deletion failure requires explicit member confirmation. Configuration reload marks disappeared instances missing. A missing membership does not automatically reactivate when an instance with the same ID returns. Retain/remove it, or uncheck and explicitly reselect the restored instance. Archiving can retain missing members. Out-of-band availability is reflected when the metadata snapshot refreshes; file changes and SQLite metadata are not a single atomic store. A file removed and recreated with the same ID between observations cannot be identified as a new incarnation; no stronger isolation is claimed.

## Administrative API

All endpoints require an active current administrator, current `operations.manage` permission and an active Console session or appropriately scoped API token. Writes (including CSRF issuance) additionally require `tools.invoke` in current role permissions and each token/delegation scope ceiling. An administrator API token with only `operations.manage` can read, but cannot create/update/delete groups. Existing tokens are not expanded. Business OAuth and management OAuth cannot manage groups. The existing four management MCP tools and their resource/scope ceilings are unchanged; this slice registers no additional MCP tool.

| Method and path | Operation |
|---|---|
| `GET /v1/mcp/groups` | Search group names, descriptions or IDs; filter `status=active/archived/all`, `q`, `offset`, `limit` (maximum 100) |
| `GET /v1/mcp/groups/instances` | Search complete instance names/IDs with pagination; optional `group_id` or `ungrouped=true`; `refresh=true` rebuilds metadata only |
| `GET /v1/mcp/groups/requests/{request_key}` | Reconcile the current actor's saved creation result; absence does not prove an earlier request failed |
| `GET /v1/mcp/groups/{id}` | Read saved metadata, revision and member IDs/availability |
| `GET /v1/mcp/groups/{id}/catalog` | Read currently visible contract-variant summaries; complete `q` search before `offset`/`limit` pagination (maximum 100) |
| `GET /v1/mcp/groups/{id}/catalog/{variant_id}` | Reread the visible variant and paginate its original instance/tool IDs (maximum 100 members per response) |
| `POST /v1/mcp/groups/csrf` | Obtain a short-lived session/body/method/target-bound, single-use ticket using `action`, `request_digest`, and a group ID for update/delete |
| `POST /v1/mcp/groups` | Create explicitly confirmed metadata and memberships |
| `PUT /v1/mcp/groups/{id}` | Replace metadata/members with `expected_revision` CAS |
| `DELETE /v1/mcp/groups/{id}` | Delete metadata/relations with `expected_revision` and `confirmed=true` |

Create/update use `name`, `description`, `status`, distinct `members` IDs, optional explicit `reconfirm_members`, and `confirmed=true`. Unknown fields and unavailable new/reconfirmed members are rejected. Browser writes require a strict same Origin and an `X-CSRF-Token` ticket bound to the SHA-256 of canonical sorted-key JSON. API tokens retain their own scope ceiling. Updates and deletion recheck live authority inside the writer transaction; revision conflict or audit failure leaves the mutation unapplied. Audit records commit with metadata changes.

Creation also requires a 32-character lowercase hexadecimal `request_key`. Its canonical sorted-key request-body digest, actor ID and group ID commit with metadata and audit. Retrying the same actor/key/body returns the same group's current revision without applying the creation again; a changed body returns `group_request_conflict`. Receipts survive group deletion: replay returns `group_request_deleted`, never resurrecting the group. Other actors cannot look up a receipt. Receipts have no TTL or automatic deletion, but their hard capacity is 10,000 per actor and 100,000 across Gate. After checking for an existing receipt, the same writer transaction checks both limits before creating a new group. At capacity, only new creation is blocked with HTTP 429 `group_request_capacity`; no group, receipt or audit mutation commits. Existing receipt queries/replays and group updates/deletion remain available. Deleting a group does not free receipt capacity; deleting the actor cascades its receipts. Do not reuse a key for another creation.

Console requests are bounded to 15 seconds each and writes are never automatically replayed. A timeout leaves completion unconfirmed. A creation draft retains its key and submitted body for explicit retry; changed edits must first use **Check saved result** or **Retry original creation**. Recovery binds the editor to the existing group and preserves current edits for a subsequent explicit CAS update. A new key is generated only for a new draft or after a definite noncommitting rejection; closing an unconfirmed creation warns that it does not delete a possibly saved group. Errors remain visible, edits remain intact on failure, and reload/dirty close require an explicit discard decision. Pending writes block duplicate submit and dismissal; late catalog/detail responses cannot replace a newer selection or closed editor.

Once a creation result is unconfirmed, Console stores only its request key in `sessionStorage`, bound to the authenticated `/v1/auth/me` user ID and current Gate origin. It stores no submitted body or credentials. Reloading and opening Groups offers an explicit read-only **Check saved result**; unsaved editing content cannot be restored. A failed query or GET 404 retains the key and never starts another creation. New creation stays disabled until successful reconciliation or confirmed **Abandon recovery record**; abandoning does not delete a possibly saved group. Confirmed discard of the original unconfirmed editor also forgets its recovery key. Switching users does not expose or clear another user's key. This is same-tab browser recovery, not server draft storage; unavailable browser storage is reported and cannot support reload recovery. A definite first-attempt capacity rejection preserves the draft without treating that attempt as an unknown creation.

## Read-only contract candidates

The catalog endpoints retain the current administrator/`operations.manage` boundary and additionally intersect freshly read tool control permissions and token/delegation ceilings with the existing tool policy. A metadata-only token can read group metadata while receiving an empty tool catalog. Business and management OAuth gain no endpoint or scope. Only active, still-present group members and exact Registry-owned MCP identities participate; built-in tools, forged IDs and deleted/recreated members awaiting explicit reconfirmation are excluded. Totals, variant counts, member counts, search and detail pages derive only from the caller's visible tools. A hidden, changed or removed variant returns the same 404. Successful responses use `Cache-Control: no-store`.

Tools with the same exact original name share a candidate only when input and output declarations normalize identically and their current published, fingerprint-matched Gate review agrees. The review comparison includes required read/write access, destructive/idempotent/open-world properties and review-bound permission, control, sensitive-field and annotation metadata. Downstream `readOnlyHint` never supplies or reduces required access. Object keys are sorted; arrays, types and schema keywords remain intact. Missing output schema differs from `{}`. This is conservative declaration comparison, not schema validation, reference resolution or a proof of equivalent business behavior. Every response says `business_equivalence: unverified`.

Different contracts remain explicit variants. Pending, stale or unreviewed contracts are never aggregated; where existing administrator policy permits viewing them, they stay individual `review_required` entries. Unrepresentable or over-complex individual contracts are `uncomparable`. A single reviewed visible member is `single_member`; multiple visible members of one reviewed contract are `reviewed_contract_match`. Variant IDs belong only to this read-only view: they are not registered tools, callable aliases or routing targets. Member detail preserves the original tool IDs and direct-call interfaces.

Each query uses a fresh Registry/authorization snapshot. The existing metadata cache contains only instance IDs/names; no tool-access decision, candidate result or member visibility is cached. A GET does not synchronize classifications, publish reviews, change grants, reconnect services or call downstream tools. Waiting on the configuration lock triggers another current-permission/token check. Search covers the full visible catalog before pagination; each page is a new snapshot, so changing membership or authorization can change later pages.

Comparison is bounded to 50,000 visible tools and 32 MiB of normalized contracts per request; exceeding either returns HTTP 503 `group_catalog_capacity` without partial results. Individual JSON contracts are bounded to 128 KiB, 10,000 visited nodes and depth 64. The regression uses 5,000 actual synthetic Registry definitions across 100 real synthetic configuration files, published test reviews, full-catalog search and nested member pagination. It makes no live downstream-connectivity or production-latency claim. The Console group editor is unchanged; these directory queries have no new UI yet.

## Support boundary

Business-equivalence confirmation, persistent schema revision directories, Agent routing envelopes, automatic future-instance authorization and session binding are **not implemented in this slice**. Contract candidates do not create callable logical tools, endpoint routing or cross-instance retry/failover. Shared downstream clients and per-call user-credential clients retain their existing lifecycle; this feature makes no browser-session isolation claim. The Git transport and isolated worker readiness gap is unchanged.
